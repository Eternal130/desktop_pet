**判定：骨架扎实，收尾潦草。** 核心架构（进程隔离的 WebSocket+JSON、控制器作为服务端）对于桌面宠物是正确的设计——进程隔离意味着 Cubism/OpenGL 崩溃不会拖垮 JavaFX 面板。无需架构返工。但执行债务在四个维度积累：**陈旧文档 + 死代码**、**手工同步的协议契约**、**线程正确性缺口**、**网络暴露面**。

1. 🚨 **WebSocket 服务端绑定 `0.0.0.0` 且零认证**——局域网内任意主机可获得渲染器完全控制权（`PetWebSocketServer.java:28`）。PoC 已确认。

## 安全发现详解

### S1. 网络暴露的无认证 WebSocket 服务端 —— 已确认，高危

**PoC 验证通过。** `new InetSocketAddress(int port)` 按 Java SE 规范使用通配地址 → 绑定 `0.0.0.0`。`setReuseAddr(true)`（`AppOrchestrator.java:124`）仅设置 `SO_REUSEADDR`，不改变绑定网卡。零认证：`onOpen` 仅校验 `instance_id` 存在且为整数（任意值）。

**影响：** 局域网任意主机以 `/?instance_id=0` 连接即可下发任意命令——`shutdown`、窗口劫持、任意音频播放、模型加载。CVSS ≈ 7.6 `AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`。隔离家庭网络中为中危，咖啡厅/企业/宿舍 WiFi 中为高危。

**修复（1 行）：**
```java
super(new InetSocketAddress("127.0.0.1", port));
```
**纵深防御：** 通过 `--token` CLI 参数添加每进程随机令牌，在 `onOpen` 中校验——防御 DNS 重绑定（loopback 模式下唯一幸存的攻击）。

### S2. 实例 ID 欺骗 → DoS + 劫持 —— 已确认，中危

`instance_id` 为硬编码常量 `0`（`AppOrchestrator.java:38` `LEGACY_INSTANCE_ID`），经 `ProcessManager` 原样透传至渲染器 CLI。极易猜测。冲突时 `PetWebSocketServer.java:43` 关闭合法渲染器连接并将攻击者注册为实例 0。**静默劫持**——攻击者可吞没命令或冒充渲染器。

**修复：** S1 修复后（loopback）此项不可远程利用。结构性修复：在查询串中要求共享密钥令牌；冲突时**不要**自动关闭既有连接。

### S3 / S4. 路径处理 —— 低危（纵深防御）

- **`load_model` 路径穿越（S3）：** 缺陷确认（`modelPath` 未净化、`FileExists` 无规范化），但 PoC **证伪任意读取**——双重 `modelPath` 约束（`<P>/<P>.model3.json`）意味着无系统文件能同时满足目录和文件名两半。仅无价值的存在性探测。
- **`play_motion_ext`/`play_audio` 绝对路径（S4）：** 超出原始范围但标记——这些接受任意绝对路径，无 Resources 前缀，是更强的文件存在性探测。仅在 S1 失败后可达；无论如何都应通过路径白名单修复。

## 架构发现详解

### A1. 控制器 ↔ 渲染器解耦 —— 合理

进程隔离是此领域的杀手级特性：Cubism SDK 崩溃、GL 驱动 bug 或畸形模型文件只拖垮渲染器，不拖垮常驻 JavaFX 面板。替代方案均不适配：JNI 丧失隔离并将 GLFW 生命周期塞入 GC 世界；命名管道为微秒级收益牺牲 `wscat`/浏览器工具；共享内存适合像素传输而非控制平面。Controller=服务端 / Renderer=客户端的方向也正确——长生命周期的编排者持有端口，临时工作者重启后重连。

### A2. 死代码 AppOrchestrator + 文档漂移 —— 删除 + 重新生成

向 `MainWindowController`（多实例、按实例 Map）的迁移在功能上已完成——单实例只是多实例的退化情形。保留 735 行死代码"为未来单实例路径"是 YAGNI 违规。**行动：** 删除 `AppOrchestrator.java`，从 `8b8eebb` 重新生成 AGENTS.md，添加 CI 文档漂移门禁。

### A3. 协议契约漂移 —— 经典反模式 **[✅ 文档侧已修复]**

> **状态更新（2026-07-10）**：`docs/protocol/commands.md` 已回填全部 6 个缺失命令（set_size/set_fps/set_hit_areas/set_layout/get_layout/reset_layout）；`error-codes.md` 与 `renderer/README.md` §1.6 的错误码已同步为正确值；5003（未知 action）与 6001（handler 异常）已分离。剩余建议：添加双端合规性测试以永久阻止未来漂移。

`Protocol.java` 与 `Protocol.hpp` 是两份手工维护的契约副本，必然漂移。症状：6 个未文档化命令在用、3/25 常量镜像（其余为硬编码字面量）、错误码冲突（4001/5001/6001/8001）、5003 同时表示"未知 action"和"处理器异常"。24 个提交的 protobuf 生成代码暗示曾尝试代码生成但搞砸了（构建不重新生成）。

**务实修复（非完整代码生成——约 25 条命令时过度设计）：** 一个遍历单一 JSON 规范的合规性测试，断言双方在每个 action/错误码/方向上一致。立即回填缺失的 6 个命令到文档。

## 代码质量发现详解

### Q1. protobuf 生成代码提交入库（高）
24 个文件位于 `controller/src/main/java/com/desktoppet/bundle/`，全部带有"Generated by the protocol buffer compiler. DO NOT EDIT!"——讽刺地还有 `// NO CHECKED-IN PROTOBUF GENCODE`。30 处 `@SuppressWarnings("serial")` 全在这些文件中。**删除它们 + 接线 `protobuf-maven-plugin` 可一并解决两个发现。**

### Q2. 线程正确性缺口
- `ProcessManager.process`（第 33 行）非 volatile，却在 `process.onExit()` 回收线程中被读。应将 `process`、`exitCallback`、`shutdownCommandSender` 标记为 volatile。
- `monitorExecutor` 无重复调度防护——应跟踪 `ScheduledFuture<?>`，取消并替换。
- `performFullShutdown` 在 FX 线程上串行忙等每个实例的停止（每个最长 5 秒）。应移至后台执行器或并行停止。

### Q3. 规范违规
`Thread.sleep()` 出现在 3 处生产代码 + 裸 `new Thread()` 于 `ProcessManager:122`。均有惯用替代（`ScheduledExecutorService.schedule`、托管执行器）。5 个空 catch 块（表面问题）。

## 项目健康发现详解

### H1. 测试覆盖欺骗
C++ `CMakeLists.txt` 仅编译 `test_stats_payload.cpp`（4 例）。`ProtocolTest.cpp`（11 例）和 `MessageHandlerTest.cpp`（6 例）是**孤立的死代码**——已编写但从未构建。C++ 实际覆盖率约 4%（1/23 源文件）。renderer AGENTS.md 甚至把这些测试用例数当作已运行的来记录。**修复：** 4 行 CMake。

Java 覆盖更健康（约 35–47% 直接/间接测试），但 `TrayManager`、`SettingsPageController`、`InstanceConfigManager`、`HitAreaCacheManager`、`AudioMapping` 零测试。

### H2. 构建可移植性
`mvnw.cmd` 是 25 行手写脚本，硬编码 `C:\Program Files\OpenLogic\jdk-21.0.8.9-hotspot` 和用户特定的缓存 Maven 3.8.5 路径。声明的 wrapper（`.mvn/wrapper/maven-wrapper.properties`）为 3.9.9。**在其他机器上必失败。** 用官方 `mvn -N wrapper:wrapper` 输出替换。

### H3. 依赖新鲜度 —— 良好
JavaFX 21.0.5 LTS ✓（满足 AGENTS.md 要求，非 25.x）、Mockito 5.14.2 ✓（支持 doReturn）、JUnit 5.11.4 ✓、Gson 2.13.2 ✓、SLF4J 2.0.17 ✓、oshi 6.6.5 ✓。无版本冲突。
